# Руководство администратора — mcp-configurator v1.2.0

Кому читать: тому, кто ставит, обновляет и обслуживает систему на машине
разработки 1С. Рабочие сценарии — в РУКОВОДСТВО-ПОЛЬЗОВАТЕЛЯ.md.

## 1. Состав поставки

| Каталог/файл | Что это |
|---|---|
| `install.ps1` | установщик (PowerShell, прав администратора не требует) |
| `snegopat-client-*.zip` | Снегопат 3.0.66 (сток, полный комплект без обрезки); установщик сам интегрирует мост |
| `bin\` | DynamicWrapperX 2.2.0.0: `dynwrapx.dll` (x64), `dynwrapx32.dll` (x86), справка |
| `mcp-configurator\` | проект: MCP-сервер (47 инструментов), исходники моста, пакетные инструменты cf (`build_ext`, `cf_diff`, `cf_inspect`, `ref_check`, `mcp_to_line`, `mockup_init`, `form_xml`, `form_text`, `make_snegopat_set`), тесты (88), доки этапов |
| `УСТАНОВКА.txt` | краткая памятка (5 строк установки) |

## 2. Требования

- Windows 10+; сеанс с обычными правами (админ не нужен: всё ставится per-user);
- **платформа 1С 8.3.27.2074** — `C:\Program Files\1cv8\8.3.27.2074\bin\1cv8.exe`
  (другие версии не поддерживаются: слоты движка снимались под 8.3.27);
- **Python ≥ 3.11** в PATH; для `pip install -e server` нужен доступ к PyPI
  (пакет `mcp`);
- **путь установки любой** (без кириллицы): с v1.2.0 мост не привязан к диску —
  дом задаётся `-HomeDir`, мост находит его через env `MCP_SNEGOPAT_HOME`
  (ставит установщик) и маркер `mcp\mcp_bridge.home`.

## 3. Установка

Из корня распакованной поставки:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File install.ps1 -HomeDir C:\Snegopat-mcp
```

Ключи: `-HomeDir <путь>` (дом), `-SnegopatZip <путь>` (другая сборка/версия
Снегопата), `-SkipPip`, `-SkipSnegopat`.

Установщик делает по порядку:
1. проверяет Python, платформу (предупреждение, не отказ);
2. распаковывает Снегопат в `<дом>\snegopat\<версия>\x64` (версия — из
   `version.json` архива; прежняя сборка уезжает в `x64-backup-<штамп>`);
   **main.js не патчится — полный функционал Снегопата**;
3. кладёт мост в `addins\mcp\` и включает его в `data\Snegopat\settings\snegopat.set`
   (пользовательский аддин; генератор `make_snegopat_set.py` — заводской список
   сохраняется, добавляется только лист моста);
4. создаёт каталоги моста, **маркер** `mcp\mcp_bridge.home`, флаг `mcp_bridge.on`;
5. создаёт конфиг сервера — **только при отсутствии** (существующий НИКОГДА
   не перезаписывается: в нём own_bases и allow-флаги владельца);
6. ставит env пользователя `MCP_SNEGOPAT_HOME` / `MCP_SNEGOPAT_CONFIG`;
7. регистрирует DynamicWrapperX per-user (HKCU);
8. копирует проект в `<дом>\mcp-configurator` и делает `pip install -e server`;
9. запускает стартер установленной версии (cwd = её x64).

## 4. Ручные шаги после установки

1. **ZCode**: в `~/.zcode/cli/config.json` → `mcp.servers` добавить
   `"mcp-snegopat": { "command": "mcp-snegopat" }`
   (env `MCP_SNEGOPAT_CONFIG` уже в User-окружении);
2. **Свои базы**: в `own_bases` конфига дописать базы, с которыми разрешена
   запись через мост, в формате `File="<путь>";` — это ГЕЙТ всех операций
   записи/обновления БД;
3. **Проверка**: открыть конфигуратор (см. §5) → в ZCode вызвать
   `list_sessions` → сессия с `bridge: "1.2"`, `home` и `journal`.

## 5. Запуск конфигуратора и версии Снегопата

Порядок строгий:
1. `starter.exe` нужной версии запущен (резидентно; cwd = его x64);
2. конфигуратор запускать **строго** `1cv8.exe DESIGNER /F <база>` — без слова
   `DESIGNER` откроется лаунчер «Запуск 1С:Предприятия» и повиснет.

Версии живут параллельно: `<дом>\snegopat\3.0.66\`, `<дом>\snegopat\1.6.43\`…
Каждая несёт свой мост (addons\mcp) и свой snegopat.set; общий дом
(`<дом>\mcp`) находится мостом автоматически. Переключение версии = запуск
стартера той версии (предварительно закрыв конфигуратор и прежний стартер).

## 6. Обновление

- **проект**: `git pull` в `<дом>\mcp-configurator` + `pip install -e server`
  (зависимости редко меняются);
- **мост**: после правок `bridge/mcp_bridge.js` — скопировать в
  `addins\mcp\` КАЖДОЙ установленной версии Снегопата и перезапустить
  конфигуратор; парсить JS через `pip install esprima` (cscript кириллические
  идентификаторы не парсит);
- **новая версия Снегопата**: тот же `install.ps1` с `-SnegopatZip
  <новый snegopat-client-*.zip>` — установится параллельно;
- **новый релиз**: распаковать поставку, запустить `install.ps1`.

## 7. Эксплуатация и обслуживание

**Диск.** Прогоны на больших конфигурациях требуют транзита ~15 ГБ
(`verify\<работа>\diff\`). При «UpdateDBCfg молча FAIL» первым делом проверяйте
свободное место. Чистка: `verify\<старые работы>\`, `backups\*.cf` старых
прогонов.

**Каталоги.** `mcp\sessions\<pid>\` живых конфигураторов НЕ УДАЛЯТЬ. Журнал:
`mcp\journal\<pid>.jsonl` (UTF-16) с автоматической ротацией (см. §8).
`backups\` — cf-откаты (config_save).

**Диагностика.** Мост при загрузке пишет `<дом>\mcp\mcp_bridge-load.txt`
(дом, pid, время) — если маркера нет после старта конфигуратора, мост не
загрузился: смотрите `x64\logs\script-errors.txt` установленной версии.
`session_info → stat/home/journal` — состояние; `report.json`/
`handoff-<штамп>.json` — вердикты конвейеров.

## 8. Журнал регистрации и типовые проблемы

**Журнал** настраивается из агента: `journal_configure(enabled, kinds, max_mb,
keep)` — пишет `mcp\mcp_bridge.cfg.json`, мост применяет без перезапуска.
**Doctor**: `doctor(session)` (47-й инструмент) или `python server\tools\doctor.py
--home <дом>` — самодиагностика всей цепочки (платформа/стартер/маркер/флаг/
конфиг/DWX/журнал/живая сессия) c вердиктом ok/warn/fail и подсказками. При
любом «не работает» — первый вызов.
Конфигурация пишется и в конфиг сервера (md_journal читает по умолчанию).

**Журнал регистрации ИБ** — не метаданные и не относится к мосту: это журнал
платформы (каталог `1Cv8Log`). Инструмент `eventlog` (48-й, внешнее соединение
V83.COMConnector, конфигуратор базы закрыть): get/set событий (`_$Data$_.Update`,
`_$InfoBase$_.ConfigUpdate`, … — 68 имён), split (период разделения хранения,
8.3.20+, монопольный доступ), dump (журнал в XML). Все события по умолчанию
ВКЛЮЧЕНЫ платформой. Если COM даёт «Библиотека не зарегистрирована» — typelib
comcntr не зарегистрирован: `eventlog` выполнит per-user регистрацию сам
(без прав администратора); полная регистрация — `regsvr32 comcntr.dll` от
администратора (делается установкой платформы, на машинах с несколькими
версиями часто отсутствует).

| Симптом | Причина | Действие |
|---|---|---|
| `list_sessions` пуст при запущенном 1cv8 | стартер не был запущен ДО 1cv8 | закрыть 1cv8, запустить `starter.exe` той версии из `snegopat\<версия>\x64`, открыть конфигуратор заново |
| конфигуратор висит на «Запуск 1С:Предприятия» | запуск без слова `DESIGNER` | запускать `1cv8.exe DESIGNER /F <база>` |
| нет `mcp_bridge-load.txt` в `<дом>\mcp\` | мост не загрузился | см. `script-errors.txt` версии; проверить snegopat.set (лист моста) |
| пакетный вызов падает «1Cv8.cdn…» | база открыта живым конфигуратором | работать по КОПИИ базы или закрыть конфигуратор |
| пакетный `/LoadCfg` висит (600+ с, лог пуст, temp-база не создаётся) | известная ловушка пакетной загрузки cf на файловой базе (этап 8 §3.2) | НЕ использовать пакетный /LoadCfg: cf грузить штатной командой конфигуратора через мост (`cfg_load_cf`-конвейер form_set_xml), XML-выгрузку — из живой сессии |
| «Cannot create object DynamicWrapperX» | DWX не зарегистрирован в профиле | `regsvr32 /i <дом>\bin\dynwrapx.dll` (без админа) |
| journal_configure не применился | мост < 1.2 | обновить мост (§6) |
| eventlog: «Библиотека не зарегистрирована» / COMConnect падает | typelib comcntr не зарегистрирован (несколько версий платформы) или база занята конфигуратором | инструмент сам регистрирует typelib per-user; базу освободить (монопольный доступ) |
| eventlog: «Существуют активные сеансы работы с данной ИБ…» | к ИБ подключён живый конфигуратор/клиент той же версии платформы — COM-соединение не поднимется | работать по копии ИБ либо на время закрыть сеансы; ограничение COMConnector, не баг |
| pip install падает | нет сети/PyPI | `install.ps1 -SkipPip`, поставить `mcp` из внутреннего зеркала |
| .ps1 с кириллицей не парсится | файл без UTF-8 BOM | пересохранить с BOM (PowerShell 5.1 читает без BOM в cp1251) |

## 9. Безопасность

- Запись в метаданные разрешена только базам из `own_bases` конфига — гейт
  сервера; не добавляйте туда продуктивные базы.
- Конфиг сервера установщик не перезаписывает — правки владельца сохраняются.
- DynamicWrapperX зарегистрирован в HKCU (влияет только на сеанс пользователя);
  отозвать: `regsvr32 /u <путь>`.
- Флаг `mcp_bridge.on` — рубильник моста.
- Журнал `md_journal` содержит имена объектов и типы правок, но не данные.


## 3. Установка

Из корня распакованной поставки:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File install.ps1
```

Ключи: `-Drive Y` (другой диск — НЕ рекомендуется, см. выше), `-SkipPip`,
`-SkipSnegopat`.

Установщик делает по порядку:
1. проверяет платформу, Python, наличие диска;
2. ставит Снегопат в `Y:\Snegopat-mcp\x64` (прежняя сборка уезжает в
   `x64-backup-<штамп>` — откат = вернуть каталог обратно);
3. создаёт каталоги моста (`mcp\sessions`, `mcp\journal`, `mcp\forms`,
   `backups`, `bin`, `verify`, `temp`) и **флаг включения**
   `Y:\Snegopat-mcp\mcp\mcp_bridge.on` (без него мост не ставит таймер);
4. создаёт конфиг сервера `Y:\Snegopat-mcp\mcp\mcp_snegopat.json` из примера;
5. копирует DynamicWrapperX в `bin\` и регистрирует **per-user** (HKCU):
   `regsvr32 /i <путь>\dynwrapx.dll`;
6. копирует проект в `Y:\mcp-configurator` и делает `pip install -e server`;
7. запускает `starter.exe` **с рабочим каталогом `x64`** (резидентный инжектор
   моста — должен висеть процессом всегда).

## 4. Ручные шаги после установки

1. **ZCode**: в `~/.zcode/cli/config.json` → `mcp.servers` добавить
   `"mcp-snegopat": {"command": "mcp-snegopat"}`
   (конфиг сервера ищется в `MCP_SNEGOPAT_CONFIG` или
   `%LOCALAPPDATA%\mcp-snegopat\config.json`; установщик кладёт его в
   `Y:\Snegopat-mcp\mcp\mcp_snegopat.json` — пропишите путь в env).
2. **Свои базы**: в `own_bases` конфига дописать базы, с которыми разрешена
   запись через мост, в формате `File="<путь>";` — это ГЕЙТ всех операций
   записи/обновления БД.
3. **Проверка**: открыть конфигуратор (см. §5) → в ZCode вызвать
   `list_sessions` → сессия с `bridge: "1.1"` и полем `journal`.

## 5. Запуск конфигуратора

Порядок строгий:
1. `starter.exe` запущен (резидентно; если умер — стартовать из `x64`, cwd
   важен: инжектор ищет модули относительно него);
2. конфигуратор запускать **строго** `1cv8.exe DESIGNER /F <база>` — без слова
   `DESIGNER` откроется лаунчер «Запуск 1С:Предприятия» и повиснет; из
   Git Bash аргументы искажаются (MSYS) — запускайте через python-subprocess
   или ярлык.

Признак живого моста: каталог `Y:\Snegopat-mcp\mcp\sessions\<pid>\` появился,
`list_sessions` видит сессию.

## 6. Обновление

- **проект**: `git pull` в `Y:\mcp-configurator` + `pip install -e server`
  (зависимости редко меняются);
- **мост**: после правок `bridge/mcp_bridge.js` — скопировать в
  `x64\modules\snegopat\addins\mcp\` и **перезапустить конфигуратор**
  (аддин грузится на старте); парсить JS через `pip install esprima` (cscript
  кириллические идентификаторы не парсит, Node не обязателен);
- **снегопат-сборка**: установщик поверх (старая уедет в backup) либо вручную
  с сохранением `data\` (настройки пользователя);
- **новый релиз**: распаковать поставку, запустить `install.ps1`.

## 7. Эксплуатация и обслуживание

**Диск.** Прогоны на больших конфигурациях требуют транзита ~15 ГБ
(слоты + полные выгрузки в `verify\<работа>\diff\`). При «UpdateDBCfg молча
FAIL» первым делом проверяйте свободное место. Чистка по мере надобности:
`Y:\Snegopat-mcp\verify\<старые работы>\`, `backups\*.cf` старых прогонов.

**Каталоги.** `mcp\sessions\<pid>\` живых конфигураторов НЕ УДАЛЯТЬ (аддин не
пересоздаёт — сессия выпадет из моста). `mcp\journal\<pid>.jsonl` — журнал
правок (UTF-16), ротация вручную при разрастании. `backups\` — cf-откаты
(config_save) — хранить до уверенности.

**Журнал вызовов/ошибок**: `x64\logs\script-errors.txt` (JScript-ошибки
аддинов), `session_info → stat` (ticks/errors/lastError) — первая точка
диагностики; `report.json`/`handoff-*.json` в рабочих каталогах — вердикты
конвейеров.

## 8. Типовые проблемы

| Симптом | Причина | Действие |
|---|---|---|
| `list_sessions` пуст при запущенном 1cv8 | стартер не был запущен ДО 1cv8 | закрыть 1cv8, запустить `starter.exe` из `x64`, открыть конфигуратор заново |
| конфигуратор висит на «Запуск 1С:Предприятия» | запуск без слова `DESIGNER` | запускать `1cv8.exe DESIGNER /F <база>` |
| пакетный вызов падает «1Cv8.cdn. Схема не зарегистрирована» | база открыта живым конфигуратором | работать по КОПИИ базы (`ext_dump_cfe` делает сам) или закрыть конфигуратор |
| «Cannot create object DynamicWrapperX» | DWX не зарегистрирован в этом профиле | `regsvr32 /i Y:\Snegopat-mcp\bin\dynwrapx.dll` (без админа) |
| 1cv8 (x64) не видит DWX | стоит только 32-битная v1.00 | поставить v2.2.0.0 x64 из поставки |
| `md_journal` пуст | мост < 1.1 или правок не было | обновить мост, сделать правку |
| pip install падает | нет сети/PyPI | `install.ps1 -SkipPip`, поставить `mcp` из внутреннего зеркала |
| .ps1 с кириллицей не парсится | файл без UTF-8 BOM | пересохранить с BOM (PowerShell 5.1 читает без BOM в cp1251) |

## 9. Безопасность

- Запись в метаданные разрешена только базам из `own_bases` конфига — гейт
  сервера; не добавляйте туда продуктивные базы.
- DynamicWrapperX зарегистрирован в HKCU текущего пользователя (не HKLM) —
  влияет только на его сеанс; отозвать: `regsvr32 /u <путь>`.
- Флаг `mcp_bridge.on` — рубильник моста: снять файл = мост перестаёт
  обрабатывать запросы (конфигуратор продолжает работать как обычный).
- Журнал `md_journal` содержит имена объектов и типы правок, но не данные —
  можно хранить без ограничений.

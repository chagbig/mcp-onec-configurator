# Руководство пользователя — mcp-configurator v1.2.0

Кому читать: аналитику/разработчику/агенту, который работает с конфигурацией
через инструменты. Установка и обслуживание — в РУКОВОДСТВО-АДМИНИСТРАТОРА.md.

## 1. Что это

MCP-сервер (47 инструментов) + мост Снегопата дают агенту в ZCode две среды:

- **живой конфигуратор** (открытое окно): метаданные, модули, формы (XML),
  расширения, хранилище, синтакс-проверка, обновление БД;
- **пакетные cf-инструменты** (без платформы): чтение/сравнение cf, сборка
  расширения из сравнения двух cf, доставка в базу линии, поиск ссылок.

Все записи защищены постусловиями; конвейеры честно отказывают, а не «делают
тихо криво» — вердикты читайте в ответе инструмента.

## 2. Типовые сценарии

### А. Вендор выпустил обновление + у нас доработки → расширение для линии

```
ext_build_from_cf(cf1="вендор.cf", cf2="доработанная.cf", name="МсрРел", prefix="МсрР_")
mcp_to_line --cfe <МсрРел.cfe> --ext-name МсрРел --line-base <база линии>
```

`ext_build_from_cf` сам: сравнивает cf (XML-канон платформы), заимствует
изменённые объекты, переносит реквизиты (с префиксом), **замещающие формы
(полный контент: элементы, события, модуль)**, ставит перехватчики на изменённые
модули (ИзменениеИКонтроль), **новые объекты делает собственными** (own, с
префиксом), грузит в слот, снимает cfe и проверяет: вендор цел, CheckModules,
постусловия. Повторный запуск идемпотентен (cfe байт-в-байт). Непереносимое —
в `report.json` (`manual`, `new_forms_cf2`, `new_objects_skipped`).

⚠️ База линии должна быть на **том же вендоре**, что cf1 (иначе UpdateDBCfg
упадёт — инструмент подскажет об этом внятно). Прогон на 2 ГБ паре — ~50 мин.

### Б. Точечная правка в живом конфигураторе

```
md_add_child / md_set_property / md_set_synonym / md_set_type   — метаданные
module_set / module_patch (hash-страж)                          — модули
form_get_xml → правка → form_set_xml                            — формы (XML)
config_save (с cf-архивом отката) → update_db_cfg               — фиксация
```

Перед удалением объекта: `md_check_refs` — покажет, кто на него ссылается.

### В. Аудит «кто что правил» и управление журналом

```
md_journal(session, src="human")   # правки человека
md_journal(session, src="agent")   # правки агента
journal_configure(enabled=false)   # временно выключить запись
journal_configure(enabled=true, kinds=[], max_mb=20, keep=3)  # вернуть
```

Журнал пишет мост с момента старта конфигуратора: AddChild / PropChanged /
DeleteChild / Save / Close / AfterSave. `journal_configure` применяет настройки
БЕЗ перезапуска конфигуратора (мост перечитывает конфиг на каждом событии).

### В2. Журнал регистрации ИБ (eventlog) — НЕ метаданные

Настройки журнала регистрации информационной базы («Виды журнала регистрации»)
через rootObject/mdclass недоступны в принципе — их нет в метаданных
конфигурации. Управление — инструментом `eventlog` (внешнее соединение
V83.COMConnector, конфигуратор базы закрыть — нужен монопольный доступ):

```
eventlog(action="get",  base="C:\базы\ib")            # все события + период разделения
eventlog(action="set",  base=..., events=["_$InfoBase$_.ConfigUpdate"], use=False)
eventlog(action="set",  base=..., events=["all"], use=True)   # вернуть все включёнными
eventlog(action="split", base=..., events=["Месяц"])   # разделение хранения, 8.3.20+
eventlog(action="dump", base=..., out_file="log.xml")  # журнал в XML (фильтр start/end)
```

Имена событий — `_$Data$_.Update`, `_$InfoBase$_.ConfigUpdate`,
`_$InfoBase$_.DBConfigExtensionInsert` и т.п. (полный проверенный список 68 имён —
`server/tools/eventlog_cfg.py: KNOWN_EVENTS`). По умолчанию платформа пишет
ВСЕ события; выключение отдельных видов — осознанное решение. Если
V83.COMConnector даёт «Библиотека не зарегистрирована», инструмент сам
выполнит per-user регистрацию typelib (без прав администратора). Выгрузка
журнала — обычный XML (`v8e:EventLog`). Ограничение: при живом конфигураторе
этой же ИБ COM-соединение не поднимется («Существуют активные сеансы…») —
работайте по копии базы либо закройте сеансы.

### Г. Формы

`form_get_xml` читает XML формы из cf (кэш), после правки `form_set_xml` пишет
через временную базу с верификацией. В конвейере (сценарий А) формы переносятся
автоматически.

## 4. Границы (сознательные)

- Общие формы в конвейере форм-замещений не переносятся (в отчёте);
  живая работа с ними — через form_get_xml/form_set_xml.
- Новая форма cf2 без оригинала в cf1 — в отчёт (привязки не проверить).
- `md_check_refs` не видит ссылки в правах ролей, подписках и текстах запросов.
- Модули новых объектов: ссылки на другие НОВЫЕ объекты требуют ручной правки
  имён (на вендорские — валидны как есть).
- Прочие версии платформы (8.3.28+) — не поддерживаются.
- `cf_recdiff` — триаж, не замена канона: имена видов объектов в записях
  контейнера отсутствуют, финальную семантику снимает cf_diff.
- Настройки журнала регистрации ИБ — вне SnegAPI (не метаданные): только
  `eventlog` (внешнее соединение, монопольный доступ).

## 5. Если что-то пошло не так

- вердикт шага и хвост лога — в ответе инструмента и в `report.json`
  (конвейер) / `handoff-<штамп>.json` (доставка);
- живые ошибки JScript — `Y:\Snegopat-mcp\x64\logs\script-errors.txt`,
  счётчики — `session_info → stat`;
- первый вызов при любом сбое — `doctor` (вердикт + подсказки);
- полный список ловушек — `mcp-configurator\docs\` (доки этапов 02–20) и
  README.md.

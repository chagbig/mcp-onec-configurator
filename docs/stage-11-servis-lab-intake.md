# Этап 11 — отдельный вход «лаба» в сервис проверки `laba1c/servis`

Ред. 1, 17.10.2026. Решение владельца: «1 Отдельный вход» — агент-кандидат (Hermes + модель Интелиона на ВМ 31041
`kandidat-1c`) сдаёт работу как стажёр, но не через Telegram (бот не может писать боту).

## 1. Постановка

Сейчас в сервисе два официальных входа (README `laba1c/servis` @ `7e17b3a`):
таблица кандидатов (`service.py poll`, только ОУ-1) и бот приёма стажёров (`review1c/intake.py`: `/add` →
приглашение → `/start` → документ `.dt`). Оба кладут работу в `works` со `state='downloaded'`; дальше одинаково —
`review1c-check` → конвейер (сторож → песочница → сопоставление → тесты → детекторы) → `works.summary`.

Нужен третий вход для агентов лаборатории, в котором стажёр-модель проходит **те же проверки и тот же режим**
(тренировка с подсказками / экзамен), что человек, и учитывается в тех же `/list`, `/profile`, `/next`, `/release`.

## 2. Архитектура: забор по HTTP, ответы — встречной отправкой

```
kandidat-1c (.117)                                   review-1c (.160)
 Hermes (пользователь hermes)                         service.py lab  (таймер, пользователь review1c)
   └─ инструмент «сдать»: DumpIB → outbox/<№>/x.dt      ├─ GET  /outbox            (список: имя, размер, sha256)
 laba-post (пользователь laba-post, :8765)  <──────────├─ GET  /outbox/<№>/<имя>  (файл, предел размера)
   outbox/ — сдачи агентов                              │   проверки = те же функции, что у бота
   inbox/<№>/ — ответы сервиса (что увидел бы человек) <─┴─ POST /inbox/<№>          (принята / подсказки / состояние)
```

* Направление соединений — **только от `review-1c`**. У `kandidat-1c` нет ни ключа, ни адреса, ни пароля к
  `review-1c`; у `review-1c` нет оболочки на `kandidat-1c` — только два HTTP-адреса.
* Посторонний в сети: общий токен `LAB_TOKEN` в заголовке обоих направлений (у сервиса — `secrets.env`, у
  `laba-post` — файл 0600 пользователя `laba-post`, Hermes его не читает) + nftables на `kandidat-1c`: порт 8765
  открыт только адресу `review-1c`. Правило выкладывается тем же скриптом, что служба, и проверяется парой проб
  (с `.160` — проходит, с другой машины — отброшено).
* Номер стажёра `<№>` — номер в `trainees` сервиса; каталог `outbox/<№>` принадлежит профилю Hermes этого стажёра.

## 3. Изменения сервиса (`laba1c/servis`)

| Где | Что |
|---|---|
| `review1c/intake.py` | колонка `trainees.lab_source`; проверки сдачи вынести из `accept()` в общую функцию (задание назначено, срок экзамена, предел за сутки и попыток, расширение, размер, подпись `1CIBDmpF`, дубль по sha256, запись папки + `works`) — бот и лаба зовут ОДНУ функцию; `tell_progress` шлёт стажёру лабы через канал лабы, а не Telegram |
| владелец | `/addlab ФИО \| код \| источник [\| экзамен ЧАСЫ]` — стажёр без приглашения, привязан к источнику; `/list` показывает источник; CLI `service.py trainee addlab` |
| `review1c/lab.py` (новый) | клиент источника: список, скачивание с пределом (`read(limit+1)`), сверка sha256 списка с фактом, отправка ответа с повторами (5 попыток, как у Telegram); токен не попадает в журнал и тексты исключений |
| `service.py lab [--once]` | для каждого источника `lab_sources` из `config.json`: новые записи outbox → общая функция приёма (`works.sheet='лаба'`, ключ `лаба\|<№>\|<sha16>`) → ответ стажёру; владельцу — «📥 Сдача из лаборатории» через Hermes; затем `tell_progress` для стажёров лабы |
| `review1c-lab.service/.timer` | раз в 2 минуты; те же ограничения, что у `review1c-check` (`ProtectSystem=strict`, запись только `/srv/review1c`) |
| `tests/test_lab.py` | подставной `laba-post` на localhost (см. §6) |
| README | раздел «Этап 8: вход лаборатории» |

Что **не** меняется: конвейер, сторож, песочница, сопоставление, итог, правило `/next`, хранение и `purge`.

## 4. Сторона кандидата (`laba1c/meta-pilot`)

* `laba_post.py` — служба на stdlib (`http.server`), пользователь `laba-post`, порт 8765: `GET /outbox`,
  `GET /outbox/<№>/<имя>`, `POST /inbox/<№>`; без токена — 403 без данных; имена — только `[0-9]+/[\w.-]+\.dt`.
* Инструмент Hermes «сдать работу»: `1cv8 DESIGNER /F <база> /DumpIB <файл.dt>` под `xvfb-run`, постусловие
  (файл есть, подпись, размер), копия в `outbox/<№>/`. Инструмент «ответ проверки»: чтение `inbox/<№>/`.
* `deploy` — служба + юнит nftables в `RequiredBy` + самопроверка правила.

## 5. Инварианты

1. Агент не имеет доступа к `review-1c` (ни ключа, ни адреса в конфигурации Hermes) — все соединения инициирует сервис.
2. Агент получает ровно то, что получил бы стажёр-человек в том же режиме: эталон, выход сопоставителя, черновик
   дефектов и вердикт к нему не попадают (инвариант 2 сервиса).
3. Проверки сдачи — одна функция для бота и лабы; копии логики нет.
4. Код кандидата исполняется только в песочнице `review-1c` (конвейер не меняется).
5. Сервис забирает только из источников `lab_sources`; запись источника не может сдать за стажёра другого источника.
6. Токены — не в argv и не в журналах; на `kandidat-1c` токен не читается пользователем `hermes`.
7. Развёртывание на `review-1c` — координатор (агенту ключа нет; правило 4а).

## 6. Приёмка (`tests/test_lab.py` + регрессия)

Сценарии на подставном `laba-post`: принятая сдача (папка, `works`, `sheet='лаба'`, задание стажёра); не `.dt`;
чужая подпись; размер — заявленный и фактический; sha256 списка ≠ факту; дубль; предел за сутки и попыток;
стажёр другого источника; неизвестный №; отключённый; экзамен после срока (до и во время скачивания);
источник недоступен / отвечает 403 / битый список — без падения службы и без строк `works`; ответы: тренировка —
подсказки после `checked`, экзамен — только «проверена»; сбой отправки ответа — повтор до 5; токен-приманка не
появляется в журнале. Регрессия: `test_intake` 42/42, `test_modes` 38/38, `test_trajectory` 22/22 — общая функция
приёма не меняет поведение бота. Негативный контроль: сценарии гоняются на прежнем `accept()` (обязаны упасть
только новые). Сквозной прогон на ВМ (координатор): `/addlab` → сдача эталона ОУ-2 с `kandidat-1c` →
`checked`, итог как у эталона (тесты 10/10, сопоставление 77/77) → ответ в `inbox`.

## 6а. Кросс-ревью ред. 1 (Sonnet, 17.10.2026) — вердикт NEEDS_WORK, все находки приняты в ред. 2

Проверено по коду выборочно: H3 (`intake.py:256` — `invite_expires[:10]` при `None`), H4 (`:510-512` —
`t.tg_user is not null`), H5 (`:337-341` — `released=1` без отправки) — подтверждаются.

| № | Находка | Решение ред. 2 |
|---|---|---|
| H1 | нет учёта виденных записей outbox: отказные файлы забираются каждые 2 мин, счётчик попыток запирает стажёра за 30 мин | `meta: lab_seen|<источник>|<handle>|<sha>`; окончательный отказ помечается виденным; сетевой сбой — не попытка; лимиты лабы отдельными ключами `lab_daily` (20) и `lab_tries` |
| H2 | внутри источника профиль №3 сдаёт в `outbox/4` и читает `inbox/4` | на `kandidat-1c` — отдельный пользователь Linux на каждого стажёра-модель (`kand-<handle>`), его `outbox`/`inbox` 0750 владелец он, группа `laba-post`; сервис сверяет `trainee.lab_source == источник` и `lab_source is not null` |
| H3 | `/list` и `service.py trainee` падают на стажёре лабы | ветка «привязан / лаба:<источник> / приглашение»; тест |
| H4 | `tell_progress` не видит лабу; при расширении — двойная отправка двумя службами | два запроса: Telegram (`tg_user not null`) только в `intake.loop`, лаба (`lab_source not null`) только в `service.py lab`; заявка строки до отправки (`update … where told is not ?`, rowcount); POST идемпотентен по `(works.key, state)` |
| H5 | `/release` ставит `released=1` без отправки; `/assign` не сообщает агенту задание | канал лабы в `release` и NOTIFY; `released=1` — только после успешной отправки; при `/addlab`/`/assign` в inbox уходит назначение и `ТЗ.md` задания (только ТЗ — не эталон, не тесты) |
| M1 | после `purge` номер стажёра переиспользуется → старые файлы `outbox/<№>` чужие | путь в outbox — не номер, а случайный `lab_handle` стажёра (hex 16), выдаётся при `/addlab`; `purge` удаляет и `lab_seen` |
| M2 | частичный DumpIB в outbox уже начинается с подписи | запись в `.part` + `rename`; `laba-post` показывает только `*.dt` |
| M3 | `urllib` идёт по перенаправлениям с заголовком токена; медленная раздача держит таймер | свой opener без редиректов, хост только из `lab_sources`, общий дедлайн скачивания на запись и на проход |
| M4 | открытый HTTP, общий токен, фильтр по IP подделывается | токены раздельно по направлениям, `hmac.compare_digest`; TLS/SSH-туннель — вопрос 4 владельцу |
| M5 | сдача до срока, забранная после срока, отклоняется | время сдачи = время появления файла по `laba-post` (пользователь агенту недоступен), принимается при `появление ≤ срок` и `появление ≥ сейчас − 15 мин` |
| L1 | второй элемент `accepted_reply` содержит путь `/srv/…` | в inbox — только ответ стажёру; тест на отсутствие `/srv` |
| L2 | `accept()` не проверяет `active` | лаба отбирает `active=1 and course_end is null` |
| L3 | `insert_work` зашит на `'бот'` | параметры `sheet`, `key` |
| гип. | пропускная способность `check` (последовательно, до 3600 с) | замерить на Э4; `LAB_TOKEN` в `secrets.env` — проверить, что песочница не видит среду службы |

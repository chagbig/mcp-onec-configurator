# Идеи доработок mcp-configurator

Кандидаты в будущие этапы. Порядок — субъективная оценка ценности/объёма.

## Ближний круг (следующие релизы)

1. **Новые объекты cf2: модули и ссылки между новыми объектами.** Этап 19 переносит
   own-объекты с формами, но модули новых объектов с ссылками на другие новые
   объекты (`Документы.МсрДругой`) требуют ручной правки имён. Автоматизировать:
   карта переименований «старое → префикс-новое» применяется к текстам модулей.
2. **Роли и подписки в md_check_refs.** Сейчас ссылки в правах ролей и подписках
   не сканируются (свой формат сериализации). Добавить разбор `Roles/*.xml`
   (объекты в правах) и `EventSubscriptions`.
3. ~~**Doctor-инструмент самодиагностики.**~~ ГОТОВО (v1.2.1): `doctor` — один вызов, который проверяет:
   платформу, стартер, маркер home, флаг .on, конфиг, own_bases, DWX, журнал —
   и выдаёт вердикт с подсказками. Снимает 80% вопросов «почему не работает».
4. **Инкрементальный cf_diff без слотов.** Сейчас diff = полные выгрузки обеих cf
   (~25 мин на 2 ГБ). cf_inspect уже читает контейнер без платформы: сравнение
   сериализаций с фильтром «изменилась ли семантика» сократило бы до минут
   (риск: сериализации пересохраняются — нужен слой нормализации).
   ИССЛЕДОВАНО 08.11.2026 (185011↔p4b, probe/cf_recdiff.py): 45358/45360 записей,
   new 2 (МсрПриёмка), del 0, changed 35 — семантики единицы (root-хеш, счётчик
   346→347 в Configuration-сериализации, versions-append), остальное — миграция
   содержимого под новыми uuid (пары `len X/0` + `len 0/Y`, старая запись
   обнулена). ВЫВОД: записный скан (1–2 мин) даёт КАНДИДАТНЫЙ дельта-набор
   ~35 uuid; финальную семантику снимает XML-канон, но только по КАНДИДАТАМ
   (точечный /DumpConfigToFiles -listFile — минуты вместо 25). РЕАЛИЗАЦИЯ: сканер
   ГОТОВ (v1.2.1, cf_recdiff.py — триаж-отчёт); гибрид «кандидаты → точечные
   выгрузки → канон» — этап-кандидат v1.3.
   Ловушка сканера: inv-словарь {name: hash} схлопывает дубли имён (name/.0/.2) —
   считать Counter пар (имя, хеш), как в cfe_records_equal.
5. **CI-runner для GitLab.** .gitlab-ci.yml готов; нужен runner на Windows-машине.
   Юнит-тесты бегут без 1С — пайплайн оживёт сразу после регистрации runner'а.

## Средний круг

6. **Enterprise-смоук (1cv8c).** Автоматический запуск клиентского сеанса на
   базе с расширением (форма открывается, кнопка на месте) — закроет последний
   ручной шаг приёмки форм.
7. **Дашборд журнала.** md_journal → HTML-страница (timeline human/agent,
   фильтры по объектам) для «что делалось в конфигурации» без ZCode.
8. **Поддержка 8.3.28+.** Пересъём слотов движка и live_e2e по процедуре из
   доки этапа 6; держать параллельную установку платформы.
9. **md_dump_to_json.** Снимок всей конфигурации через cf_inspect в JSON
   (инвентарь объектов/реквизитов для диффов и отчётов без платформы).
10. **Конфигурация моста через MCP.** Помимо журнала — таймауты, LONG_OPS,
    белые списки команд: те же mcp_bridge.cfg.json + инструмент.

## Дальний круг (по решению владельца)

11. **DynamicWrapperX-контур: расширение.** Заимствование объектов контекстным
    меню, ext_open по имени, «первый реквизит ТЧ» живым деревом — DWX установлен,
    операции разблокированы, нужна обвязка в мосте.
12. **MergeCfg -Settings как арбитр diff.** Выборочная верификация diff
    платформенным объединением (34 с на 2 ГБ) поверх cf_diff.
13. **MCP over SSE / удалённый сервер.** Сейчас stdio на той же машине; SSE
    открыл бы работу агента с удалённой станцией конфигурирования.
14. **Автотесты на паре 3.0.66 + 1.6.43 в CI.** Две матрицы живого смоука по
    расписанию (требует runner + тестовые базы).

## Из сравнения mcp-edt vs mcp-configurator (09.11.2026)

Источник: `W:\Проекты\code mode 1c\сравнение-mcp-edt-vs-mcp-configurator.docx`
(MCP-EDT DitriX v2.15.1 на EDT 2025.2.5.2 vs mcp-snegopat v1.2.4). Нумерация —
продолжение списка выше; ссылки «п.4.3» и т.п. — на разделы анализа.

15. **Поиск по текстам модулей (md_search_code).** Из сравнения: п.4.3 (search_in_code).
    Сейчас md_find ищет только по именам объектов — по коду искать нечем, агент не может
    найти, где вызывается функция или где живёт логика. Реализация: разбор модулей через
    cf_inspect (без платформы) или мостом по открытым модулям; выдача «объект, процедура,
    строка, контекст». Усилие: M. Приоритет: высокий — самая частая операция при
    ревью/рефакторинге, главная дыра контура чтения.
16. **Структура модуля и иерархия вызовов (module_structure).** Из сравнения: п.4.3
    (get_module_structure, get_method_call_hierarchy). Список процедур/функций с номерами
    строк, экспортностью и директивами — номера нужны для точечных module_patch; второй
    шаг — статическая иерархия «кто кого вызывает» по текстам модулей. Усилие: S
    (структура) / M (иерархия). Приоритет: средний — навигация по большим модулям ERP,
    без номеров строк патч вслепую рискован.
17. **Каскадное переименование/удаление с переписыванием ссылок.** Из сравнения: п.4.3
    (rename/delete_metadata с каскадом ссылок). Сейчас md_delete требует явный uuid,
    md_check_refs находит ссылки лишь частично (роли/подписки не сканируются — п.2),
    а переименование не правит ссылки в чужих модулях. Карта «старое → новое» по текстам
    модулей (механика уже спроектирована в п.1). Усилие: L. Приоритет: высокий — базовый
    рефакторинг сейчас небезопасен: после удаления остаются битые ссылки.
18. **md_clone — клонирование объекта метаданных.** Из сравнения: п.4.3
    (clone_metadata_object, adopt_metadata_object). Один вызов: объект + реквизиты +
    ТЧ + формы + модуль (сейчас — длинная серия md_add_child/md_set_*). Полезно при
    массовом создании однотипных регистров/документов. Усилие: M. Приоритет: средний —
    экономия заметная, но обходится серией существующих вызовов.
19. ~~**Двухфазное подтверждение деструктивных операций.**~~ **ГОТОВО (11.11, 7c1ab7b):**
    delete/rename/update_database идут «предпросмотр → confirm»). У нас md_delete требует
    uuid, но фазы подтверждения нет: добавить предпросмотр (что удалится, какие ссылки
    останутся) + confirm=true; то же для update_db_cfg. Усилие: S. Приоритет: средний —
    uuid + md_check_refs уже снижают риск; двухфазность даёт паритет безопасности.
    РЕАЛИЗАЦИЯ: md_delete/update_db_cfg confirm=False → план (объект, ссылки, isModified), confirm=True → исполнение.
20. **Пресеты/группы инструментов и read-only режим.** Из сравнения: п.4.6 (у EDT-MCP
    11 групп, пресеты «Analysis Only»/«Code Review», progressive disclosure). Конфиг/ENV
    read_only=1: инструменты записи скрыты или отказывают; пресеты сокращают ~48
    инструментов до нужного набора. Усилие: M. Приоритет: средний — экономит контекст
    агента и снижает риск случайных правок в сценариях «только ревью».
21. ~~**Валидация запроса через COM-контур.**~~ **ГОТОВО (11.11, 7c1ab7b, 52-й инстр. query_validate):**
    режимы check (обёртка ВЫБРАТЬ ПЕРВЫЕ 1 * ИЗ (...)) и execute (read-only); вердикт ошибки 1С = результат.
    Через уже работающий V83.COMConnector (как eventlog): соединение.NewObject("Запрос"),
    выполнить read-only SELECT в транзакции с откатом и вернуть ошибку платформы —
    агент проверяет тексты запросов до вставки в модуль. Усилие: S. Приоритет: средний —
    дешёвая частая проверка; своего API проверки запросов у конфигуратора нет.
22. **Прогоны YAXUnit из MCP.** Из сравнения: п.4.3 (run_yaxunit_tests). Отладочный
    контур конфигуратора ограничен (docs/debug-brkpt-probe.md: агент ставит точки,
    ход отладки недоступен), но `1cv8.exe /Execute YaxUnit.epf` запускается командной
    строкой без моста; инструмент-обёртка: старт, ожидание, возврат отчёта. Механика
    запуска клиента смежна с п.6 (Enterprise-смоук). Усилие: M. Приоритет: средний —
    тесты закрывают «валидацию уровня IDE», которой в контуре конфигуратора нет.
23. ~~**Создание/удаление тестовых инфобаз.**~~ **ГОТОВО (11.11, 7c1ab7b, 53-й инстр. infobase):**
    create/delete двухфазно, гварды own_bases/1Cv8.1CD; ловушка: CREATEINFOBASE ломается на
    пробеле в пути (кавычки не спасают) — обход: ASCII-имя в том же каталоге + rename.
    delete_infobase). `1cv8.exe CREATEINFOBASE` из командной строки; нужно для матриц
    автотестов (п.14) и чистых прогонов. Усилие: S. Приоритет: средний — без него
    матрицы п.14 готовятся руками.
24. **Скриншот формы/окна конфигуратора.** Из сравнения: п.4.3 (скриншоты форм и
    макетов; у EDT-MCP через JVM-флаг, у нас — мышиный контур DWX: открыть форму,
    снять окно). Для визуальной верификации замещающих форм (этап 15). Усилие: M.
    Приоритет: низкий — формы уже верифицируются текстом и постусловиями; скриншот —
    бонус.
25. **Многоязычные синонимы (Ru/En).** Из сравнения: п.4.3 (переводы, LanguageTool).
    md_set_synonym пишет один язык; внутреннее представление локализуемой строки
    поддерживает пары «язык/текст» — расширить чтение/запись до Ru+En. Усилие: S.
    Приоритет: низкий — переводы нужны только для публичных/экспортных конфигураций.
26. **Контрактная карта EDT-MCP ↔ mcp-snegopat.** Из сравнения: п.6–7 (фасад onec_*
    маршрутизирует по доступности среды; эталонный Go-сервер уже называет контракты в
    терминах EDT-MCP — FUNCTIONAL_PARITY). Зафиксировать в docs соответствие
    «инструмент ↔ onec_* ↔ EDT-MCP», при необходимости — алиасы. Усилие: S. Приоритет:
    низкий — актуально, когда фасад v2 станет реальностью.
27. **Auth token / выключатель remote access для HTTP-транспорта.** Из сравнения: п.4.2
    (у EDT-MCP auth token на HTTP и выключатель remote access). Актуально только после
    п.13 (MCP over SSE): без сетевого транспорта токен не нужен. Усилие: S. Приоритет:
    низкий — заблокировано п.13.

### Уже покрыто в mcp-configurator

* get_metadata_objects / get_metadata_details → `md_tree`, `md_object`, `md_children`,
  `md_find`, `md_walk`; list_projects → не применимо (workspace EDT).
* read_module_source / write_module_source → `module_get`, `module_set`, `module_patch`.
* create / rename / delete_metadata → `md_add_child`, `md_set_property` («Имя» с
  uuid-сверкой), `md_delete` (без каскада ссылок — см. п.17).
* update_database → `update_db_cfg` (только own_bases).
* Сравнение конфигураций → `cf_diff.py` / `ext_build_from_cf` (XML-канон двух cf).
* Журнал событий ИБ → `eventlog` (V83.COMConnector, без конфигуратора).
* История MCP-вызовов → серверный журнал вызовов + `md_journal` (human/agent).
* find_references — частично: `md_check_refs` (остаток — п.2 бэклога: роли/подписки).
* Запуск клиентов из EDT → смежное: п.6 бэклога (Enterprise-смоук 1cv8c).
* MCP over SSE — уже п.13 бэклога; дубликат из сравнения не создавался.
* Уникальные сильные стороны (§5 сравнения): живая правка без XML-цикла, хранилище
  (`cfgstore_*`), конвейер расширений из cf (`ext_build_from_cf`), `doctor`.

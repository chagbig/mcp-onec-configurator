# Этап 14. Расширение из сравнения двух cf (план, ред. 1 — 28.10.2026)

## 1. Цель (ред. 2 — после ревью Kimi)

Даны cf1 (вендорский эталон) и cf2 (доработанная). Агент строит **план переноса отличий**
(diff.json с классификацией переносимости) и собирает **расширение переносимой части**,
готовит cfe-артефакт. Ручной конфигуратор не нужен.

**Классификация отличий (ревью К-1/К-2/К-3):**
| Класс отличия cf1→cf2 | Перенос | Как |
|---|---|---|
| изменённый МОДУЛЬ объекта/менеджера | ДА | заимствование (cfe-borrow) + перехватчик (cfe-patch-method: ИзменениеИКонтроль копирует тело оригинала) |
| изменённая ФОРМА | НЕТ (автоматом) | cfe-borrow даёт пустую оболочку с вырезанными привязками (К-2); отчёт + ручной перенос в живом конфигураторе (этап 13 навыки) |
| изменённые РЕКВИЗИТЫ (добавленные) | частично | собственный реквизит расширения с префиксом (расширение не может менять тип заимствованного); правка ссылок — за агентом |
| изменение ТИПА/удаление реквизита заимствованного | НЕПЕРЕНОСИМО | отчёт (К-1) |
| НОВЫЕ объекты cf2 | НЕПЕРЕНОСИМО автоматом | требуют префикс + правку всех Ref-ссылок (К-3); отчёт |
| УДАЛЁННЫЕ в cf2 объекты | НЕПЕРЕНОСИМО | расширением не воспроизводятся (К-3); отчёт |

diff.json несёт класс каждому отличию; непереносимые — в отчёт владельцу, НЕ в расширение.
Цель этапа — «расширение = перехватчики изменённых модулей + переносимые реквизиты»,
остальное — отчёт. (ред.1 обещала «отличия целиком» — недостижимо имеющимся скилом.)

## 3. Архитектура (ред. 2: гибридный diff)

```
cf1, cf2 (файлы)
→ (1) ПЕРВИЧНЫЙ ФИЛЬТР: cf_diff.py над cf_inspect — записи по uuid + hash payload;
      служебные (configinfo, version, versions) исключить. Быстро (стриминг, без выгрузок).
→ (2) РАСКРЫТИЕ изменённых: частичные выгрузки /DumpConfigToFiles -listFile
      (ТОЛЬКО изменённые объекты) из cf1 и cf2 — обе выгрузки делает ОДНА платформа,
      поэтому сериализационная нормализация НЕ нужна (закрывает ревью М-2:
      вендорские формы в cf-тексте дадут ложный diff, XML-выгрузка канонична;
      ревью М-1: вложенности записей cf нет — раскрытие только через выгрузки).
→ (3) КЛАССИФИКАЦИЯ: diff.json — объект → классы отличий (модуль/форма/реквизиты) →
      переносимость по таблице §1
→ (4) СБОРКА: cfe-init (CompatibilityMode ИЗ cf1 — cfe-init -ConfigPath, ревью М-4)
      → cfe-borrow (оболочки) → cfe-patch-method (ИзменениеИКонтроль — тело оригинала из
      выгрузки cf1; ловушка ЛинияА: собственный метод с именем оригинала ВЕШАЕТ клиент —
      проверять префикс) → собственные реквизиты с префиксом
→ (5) cfe-validate → /LoadConfigFromFiles -Extension (ключ подтверждён линией ЛинияА,
      ревью L-1; П14-1 — регрессия + негатив на НЕсуществующее имя)
→ (6) ВЕРИФИКАЦИЯ: слот (mockup_init) → /DumpCfg -Extension → cf_inspect:
      заимствованные записи по ХЕШАМ СОДЕРЖИМОГО (не файлов — ревью L-2); вендор
      cf1 vs новая база — записи по хешам; сверка diff.json → состав cfe (revie М-3);
      CheckModules -Extension (код 0)
→ (7) cfe-артефакт в линию (этап 12-механика; наследовать пакетные ловушки этапа 8 —
      ретраи, taskkill /F, зомби — ревью L-3)
```

cf_inspect остаётся read-only (ревью М-5: резерв «писать cfe-контейнер» отклонён —
полноценный реверс; резервом загрузки служат мостовые ext_save_cfe/ext_load_cfe).

## 10. build_ext — конвейер целиком (28.10.2026, ночь)

`server/tools/build_ext.py` — одна команда: cf1 + cf2 → расширение + cfe-артефакт +
отчёт. Шаги: cf_diff (слоты + полные выгрузки) → cfe-init → cfe-borrow изменённых
владельцев → **fill_shells (генератор наполнения)** → cfe-validate → слот cf1 →
Load/Check/Update -Extension → cfe → верификации.

**fill_shells (генератор):** по разнице child-объектов владельца в cf1/cf2 — новые
в cf2 части добавляются в оболочку как собственные (имя без префикса расширения
получает префикс, маппинг cf2→ext в отчёте); ТЧ, существующие в cf1, объявляются
Adopted-контейнерами с новыми реквизитами внутри; формы/команды — в отчёт (К-2).

**Прогон на малой паре (МсрТЧ43 attrs-new) — все шаги ok с первого раза:**
cf_diff (28 с) → владельцы (Документ.МсрТЧ43) → init → borrow → **наполнение:
вставка 1, маппинг МсрПервыйРеквизит → Мср14_МсрПервыйРеквизит** → validate OK →
слот cf1 → cfe 5 записей → **вендор цел (10 записей == по хешам)** →
**реквизит Мср14_МсрПервыйРеквизит верифицирован в cfe** (запись документа).

Осталось этапа 14: перехватчики изменённых модулей в конвейере (cfe-patch-method по
списку из отчёта — вызов подготовлен, но не испытан на паре с изменёнными модулями),
боевые пары с формами. П14-5 повторно не требуется: msr14v2 уже показал линию.

## 12. Разведка `/MergeCfg -Extension` (03.11.2026) — сопровождение расширений

Вопрос: умеет ли пакетный `/MergeCfg` целить в расширение (сопровождение при
обновлениях вендора)? Пробы на слоте p15 (cf2 малой пары, settings по XSD):

| Проба | Результат |
|---|---|
| `/MergeCfg <cf>` без настроек, batch | rc=1 «Запрещено использование окон» — интерактивное объединение в batch запрещено |
| `/MergeCfg <cf> -Settings <файл>` | **rc=0 «успешно завершено»** — объединение в ОСНОВНУЮ конфигурацию |
| `/MergeCfg <cf> -Settings <файл> -Extension <Имя>` | rc=1 «Запрещено использование окон» — ключ не работает пакетно |
| XSD настроек (`bin/frntend_root.res`, ns `merge/settings`) | **0 упоминаний Extension**: корень Settings = MainConfiguration/SecondConfiguration/OldVendorConfiguration/Parameters/SupportRules/Conformities/Objects |

**Вывод (8.3.27.2074): пакетного `/MergeCfg -Extension` НЕТ.** Сопровождение
расширений при обновлениях вендора — только повторный прогон `build_ext` по новой
паре (вендор обновился → cf1', доработка перезаложена → cf2'): конвейер идемпотентен
(cfe байт-в-байт), формы переносятся (этап 15). `/MergeCfg -Settings` остаётся
арбитром для основной конфигурации (этап 12, П4). Формат settings-файла — по XSD:
`<Settings version="1.0"><Objects><Configuration><MergeRule>…` + `<Object
fullNameInSecondConfiguration="…">` (плоские элементы вне `<Objects>` не парсятся —
платформа падает в интерактив).

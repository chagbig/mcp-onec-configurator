## Что сделано

### Этап 2 — мост `mcp_bridge.js` (1349 строк, JScript/ES3)

Развитие проверенного спайком `mcp_spike.js`; каталоги — **по сессии** (план §4.2):
`mcp\sessions\<pid>\{req,resp,session.json}`, файл включения `mcp_bridge.on` (инвариант 8).

* Реестр сессии: pid, строка соединения, платформа, контейнеры (`identifier`, `isModified`,
  `root`, `master`), heartbeat, текущая/долгая операция (`running`), статистика тиков.
* Идемпотентность: повтор `id` — прежний ответ из кэша (256 записей), файл запроса
  удаляется и в кэш-ветке (см. ловушку 4).
* `deadline`: истёкший запрос не выполняется (`code: "deadline"`).
* Ошибки: `{code, message, where: {op, path, uuid, prop, container}}`.
* Исполнение — только из тика (150 мс), при `!busy` и `modalMode == 0`; весь тик и все
  обработчики событий в try/catch (предел в 5 ошибок движка не задеваем).
* Атомарная запись UTF-8 c ретраями на sharing violation (читатель session.json в Python).
* Трассировка текущей операции в session.json до/после каждого вызова — при зависании видно,
  какая операция выполнялась (журнал движка буферизуется и обрывается раньше точки зависания).

Критерии этапа выполнены и проверены вживую: неизвестная операция — `unknown_op`;
6 битых запросов подряд — мост жив; повтор id — прежний ответ (`replayed` +1, `done` без
скачка); истёкший deadline — не выполняется.

### Этапы 3–4 — сервер `mcp-snegopat` (Python 3.11+, `mcp>=2.3`, stdio)

`server/mcp_snegopat/`: `bridge.py` (клиент почтового каталога, реестр сессий с проверкой
живости pid через WinAPI, журнал вызовов JSONL), `config.py` (разрешения), `winutils.py`
(активация окна конфигуратора), `server.py` (33 инструмента). Установка: `pip install -e server`.

* Выбор сессии: одна живая — автоматом; несколько — отказ со списком (pid указывается явно);
  мёртвые pid помечаются (`list_sessions` при нуле сессий — пусто без ошибки, критерий этапа 3).
* Запись — только с ожидаемым состоянием (`expected_hash` у модулей, `expected` у свойств,
  uuid при переименовании); сервер не пускает вызов без него (`bad_args`).
* `md_tree` с пагинацией по видам (критерий этапа 3: страницы, а не весь корень).
* `md_add_child`/`md_delete` — оркестрация этапа 7 на сервере: навигация по таблице классов
  владельца (`GROUP_NAV`), выделение в дереве **отдельным тиком** (ловушка 1 этапа 7),
  активация окна конфигуратора, `expectClass`/`stray` — как в сценариях этапа 7.
* `config_save`: без явного архива сам снимает cf (точка отката) и сохраняет; постусловие
  `isModified=false`.
* Конфиг: `own_bases`, `allow_store`, `allow_update_db` (умолчания — всё запрещено).

Тесты: 27 юнит-тестов на подставном мосте (`server/tests/fake_bridge.py` — поток,
обслуживающий почтовый каталог с семантикой моста) + stdio-смоук (initialize → tools/list
→ tools/call). Все зелёные.

## Ловушки живой отладки (внесены в скил)

1. **`null` в квалификаторах `v8New` вешает движок.** Сервер передавал
   `{"digits": null, ...}`; проверка `t.digits !== undefined` пропускает null →
   `v8New("КвалификаторыЧисла", null, null)` → главный поток зависает навсегда (тики
   останавливаются, heartbeat протухает). Исправлено на обеих сторонах: сервер не шлёт
   отсутствующие ключи, мост различает undefined и null.
2. **`AttachThreadInput`/`SetFocus` из чужого потока вешает 1cv8.** Первая попытка
   активации окна конфигуратора из Python attaching'ом очереди ввода приводила к
   зависанию при следующем создании окон (текстовый редактор). Убрано полностью:
   снаружи — только Alt-эмуляция + `SetForegroundWindow`; изнутри моста — `SendKeys("%")` +
   `AppActivate(pid)` **отдельным тиком** (эффект доходит очередью сообщений не сразу) —
   `activate_self` + ожидание `focusHwnd` на сервере.
3. **`hwnd` представлений в SnegAPI на 8.3.12+ всегда 0** (`com_windows.as: get_hwnd`
   возвращает 0 при `ver >= 8.3.12`). Нажатия клавиш дерева идут в окно **фокуса ввода**
   (`winApi.getFocus()`); при фоновом окне конфигуратора фокуса нет — мост отказывает
   явно (`focus_probe` — диагностика), а не шлёт нажатия в никуда.
4. **Идемпотентность: файл запроса надо удалять и в кэш-ветке.** Незакрытый «повторный»
   запрос обрабатывался каждый тик (шторм replay, в опыте — 1336 повторов), а как старейший
   в каталоге — блокировал все запросы, сортирующиеся после него.
5. **`md_find`: класс в пути ребёнка — его собственный**, а не родителя
   («Справочник.Х.Реквизит.У», не «Конфигурация.Х…»); у корня — без префикса имени корня.
6. **Несколько конфигураторов** (стартёр внедряется во все `1cv8.exe`): запросы и реестр —
   по сессиям `sessions\<pid>`; сервер при нескольких живых требует явный pid. В прогоне
   24.10 рядом оказалась чужая сессия хранилища `crtest` — не тронута.
7. **`typeToStr`: `.Типы()` по COM из JScript не вызывается** — ответ этапа 7
   `{"S",50,1}` приходит внутренней строкой; сверка типов — по internal-представлению.
8. **Журнал движка буферизуется**: последняя строка не равна точке зависания. Диагноз —
   по `session.json` (heartbeat/`running`) и трассировке текущей операции.
9. **`writeSession` ловит sharing violation** с читателем Python (файл открыт без
   FILE_SHARE_DELETE): запись с ретраями и запасной прямой перезаписью.

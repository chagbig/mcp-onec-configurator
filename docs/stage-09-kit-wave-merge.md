## Вариант B волны: один cf-источник → объединение в каждую базу

Сейчас (дорого): полная загрузка `src` в КАЖДУЮ базу слота (новые объекты → полный путь × N баз).

Предлагается:
1. Собрать cf-ИСТОЧНИК ОДИН раз — из базы, где уже есть вендорская конфигурация + наши объекты
   (база сборки после полной загрузки, либо релизный cf из `build_release.py`). `/DumpCfg`.
2. Сформировать файл настроек объединения: корень «Конфигурация» `DoNotMerge` + КАЖДЫЙ изменённый/новый
   объект `GetFromSecondConfiguration` (список берётся из `git diff <основа>...HEAD -- src`, как уже
   делает `wave_ops load --objects`).
3. В КАЖДУЮ базу слота: `/MergeCfg cf-источник -Settings` → `/UpdateDBCfg`. Быстро и хирургично:
   прочие объекты базы не трогаются.
4. Постусловие на базу — ЧАСТИЧНАЯ выгрузка изменённых объектов (`/DumpConfigToFiles -listFile`),
   не код возврата (команда моста `merge-cfg --check-object` уже так делает).

### Почему cf-источник, а не пустая конфа с объектами

Наши объекты обычно ССЫЛАЮТСЯ на вендорские (реквизит типа `CatalogRef.ВендорскийСправочник`).
В пустой конфигурации такой тип не разрешается — cf собрать нельзя. Поэтому источник — cf
ПОЛНОЙ конфигурации (вендор + наши), а настройки объединения переносят в приёмник ТОЛЬКО наши
объекты; ссылки разрешаются, потому что вендорские объекты у приёмника уже есть.
**(ТРЕБУЕТ ПРОБЫ: объект со ссылкой на вендорский — на тестовой базе.)**

### Поддержка баз слотов

Объединение в конфигурацию НА ПОДДЕРЖКЕ с запретом изменения молча не вносит ничего (проверено).
Инструмент волны обязан определять состояние поддержки каждой базы (флаг `G` в
`Ext/ParentConfigurations.bin`) и, если база на поддержке, иметь включённую «возможность изменения»
+ editable-корень (скил `support-edit`). **(ТРЕБУЕТ ПРОБЫ: на поддержке ли базы слотов CI.)**

## Порядок реализации (через KIT, не правкой vendored-копий линий)

1. **Проба на тестовой базе** (БСП демо): объект со ссылкой на вендорский объект через cf+merge;
   проверка поддержки баз слотов. — ДО кода.
2. Новая подкоманда `wave_ops.py load --вариант-cf` (или расширение `wave_cmd.py`): сборка cf-источника,
   генерация настроек из `git diff`, объединение по базам с постусловием частичной выгрузкой.
3. Мост (`onec_bridge.py`) — команда `merge-cfg` уже добавлена (постусловие частичной выгрузкой).
4. Версионирование kit (новая версия), замок kit, кросс-ревью (другая модель), проба на ОДНОЙ линии,
   затем раскладка — по `agent-parallel-work.md` (§2, §6, §9а) и `cross-review-cycle`.

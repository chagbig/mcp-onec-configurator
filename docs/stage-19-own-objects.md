# Этап 19. Новые объекты cf2 → собственные объекты расширения (05.11.2026)

## 1. Задача

Пилот (04.11) показал последний разрыв конвейера: вендорская дельта может состоять
ЦЕЛИКОМ из новых объектов (МсрПриёмка), а этап 14 уводил их в отчёт — конвейер
отказывался собирать расширение. Этап 19: новые объекты cf2 переносятся как
СОБСТВЕННЫЕ объекты расширения (с префиксом).

## 2. Реализация (`build_ext.py`)

- `create_own_object(src, dump2, dir, kind_en, name, ext_name)`: wrapper из cf2
  (новый uuid — own-объект с другим именем это другой объект; идемпотентность —
  uuid стабилен при неизменном контенте) + поддерево (формы/макеты/модули) с
  заменой квалифицированных ссылок на САМ объект.
- `_rename_refs`: Document.МсрПриёмка → Document.МсрП_МсрПриёмка, включая
  производные типы (cfg:DocumentRef.X — суффиксы Ref/Object/Selection/List/Manager);
  чужие объекты (МсрПриёмка2, Catalog.МсрПриёмка) не трогаются.
- Own = БЕЗ ObjectBelonging/ExtendedConfigurationObject (их отсутствие и есть own).
- Регистрация в `Configuration.xml`: плоская запись `<CommonForm>Имя</CommonForm>`
  в ChildObjects (платформа сортирует при загрузке).
- Ранний выход «пустое расширение» снят, если есть own-able новые объекты
  (новые объекты сами оправдывают конвейер без изменённых владельцев).
- Kinds v1: ОбщаяФорма, Документ, Справочник; прочие — new_objects_skipped.
- Постусловие 6b расширено: own-объект в выгрузке расширения, имя с префиксом,
  БЕЗ Adopted.
- Ограничение v1: ссылки в МОДУЛЯХ новых объектов на другие новые объекты
  (Документы.МсрПриёмка) не переименовываются — ручная доводка; ссылки на
  вендорские объекты валидны как есть.

прогоном); при следующем кросс-ревью включить build_ext.py целиком.

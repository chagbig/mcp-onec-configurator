## 1. Вопрос пилота

**Может ли открытая модель на российском инференсе (Интелион) по ТЗ задания из банка `laba1c/zadaniya` спроектировать
метаданные конфигурации (спецификация `meta-compile`), которые без правки человеком компилируются, грузятся в базу и
СОДЕРЖАТЕЛЬНО совпадают с эталоном — так, как это проверяет сервис оценки кандидатов?** Модель оценивается ровно как
кандидат: тем же сопоставителем ролей, по структуре, а не по именам. «Go» — по совпадению ролей (M2), не по прохождению
цепочки (M1): пустая конфигурация цепочку проходит.

Уровень L1 (пилот) — только метаданные. Уровень L2 (после L1, отдельное решение) — метаданные + модули проведения:
полная оценка сервисом (YAxUnit, детекторы, мутации) и сравнение с живыми работами кандидатов.

### 4.2. Корпус

* Задачи — 6 заданий банка; по мере роста банка (цель ~24) — те же правила. Единица — **задание целиком** (ТЗ →
  вся конфигурация); метрика — по ролям (у заданий 23–44 роли, всего ≈ 200 — разброс приемлем).
* L1 — объекты метаданных (`build/objects.json`). **Отчёты и СКД** (`skd-compile`), **формы** — вне L1: их роли
  считаются отдельной строкой «вне L1», в порог не входят.
* **Эталон** — `build/objects.json` и `src` задания. **К модели не попадает никогда** — ни в запрос, ни в обратную связь.
* **Срез** не нужен: конфигурация с нуля, вендорских объектов нет. В запрос — ТЗ и сжатая справка DSL `meta-compile`
  (отдельный версионируемый файл).
* **Утечка в обучение**: задания свои, но мотивы — открытые экзаменационные билеты (есть публичные решения, напр.
  GitHub `zeltyr/1c_platforma_spec`). Риск оценивается по разнице «ОУ (свои)» и «ЭК (по мотивам билетов)».
* **Контаминация Claude**: эталоны собирались сессиями Claude Code — Claude участвует как ориентир без порога.

## 5. Метрики, контроли, порог

| Метрика | Что меряет |
|---|---|
| **M2 — роли** (решающая) | сопоставитель сервиса (`mapper/auto_map.py --task`, правила `mapper_<код>.py`) находит роли схемы в конфигурации модели; `check_mapping` по схеме — без расхождений. M2 = доля ролей L1, найденных и прошедших проверку; по заданию и в целом. Регистры ЭК-заданий в схеме ролей не заданы — для них в L1 только «есть регистр нужного вида с движениями от нужного документа» (структурная проверка), полная проверка — L2 |
| M1 — цепочка | сторож схемы JSON → `meta-compile.py` (нормализация 2.20 и `cfg:`) → `meta-validate` → загрузка в свежую файловую базу → постусловие (обратная выгрузка) |
| M3 — цена | токены, ₽, круги, время модели и цепочки |
| M4 — выдумки | ссылки на объекты, которых нет в спецификации самой модели (ловит загрузка) — 0 |

**Контроли набора (Э1, до моделей):**
* положительный — эталонный `build/objects.json` каждого задания проходит M1, M2 = 100 % (без отчётов/форм);
* переименование — эталонная спецификация с переименованными объектами и реквизитами: M2 = 100 % (сопоставитель по
  структуре — уже доказано на `src`, повторить на спецификации);
* минимальная — по `{"type","name"}` на каждый объект эталона: M1 проходит, M2 ≈ 0 (ревью H1);
* отрицательный — порча спецификации эталона (снять колонку ТЧ, сменить тип реквизита, ссылку в никуда, переставить
  документ-регистратор): каждая — своё падение M1 или M2.

**Модели:** `qwen3.8-27b` и `qwen3.6-35b-a3b` (rus, AI API) — кандидаты; `qwen3:14b` — отрицательный контроль по M2;
Claude — ориентир без порога.

**Порог «go» (принят владельцем):** M2 ≥ **95 %** по ролям L1 после цикла, M4 = 0, ни одного задания ниже 85 %
(чтобы среднее не прятало провал целого задания); два прогона без цикла с печатью разброса.

**Бюджет:** харнесс держит дневной предел **200 ₽** (сумма по `model_api`, отказ до вызова при превышении).
Оценка: задание ≈ 25 тыс. токенов входа (ТЗ + справка DSL) и ≈ 8 тыс. выхода → 6 заданий × 5 обращений (прогон +
4 круга) ≈ 3–4 ₽ на модель по ценам Qwen3.6 35B — весь Э2–Э3 укладывается в один день.

**Воспроизводимость:** модель, квантование, регион из `/v1/models`; температура 0,2 (на повторе 0,5); `max_tokens`;
`think` выкл.; хеш банка (коммит `laba1c/zadaniya`), хеш справки DSL и скилов `meta-*`; версия платформы.

# Этап 8 — раскладка форм в XML через временную базу (план реализации, ред. 1)

26.10.2026. Исходные решения — `docs/plan-mcp-snegopat.md` §5 этап 8 и §3.1; первичка —
`docs/spike-01-demossl.md` (опыт 4а), `docs/stage-02-06-mcp-server.md`. Приёмка по правилу
«вердикт — постусловием».

## 1. Цель

Агент читает и правит **раскладку форм живой конфигурации в XML** (формат скилов
`form-edit`/`form-validate`/`form-compile`) — через временную базу, без реверса и без
правки движка. Мост уже даёт: внутренний текст живой формы при открытом редакторе
(`form_save` c хешем, `form_load` с expected_hash — ревью 25.10).

## 2. Установленные факты (первичка)

| Факт | Источник |
|---|---|

## 3. Архитектура

### 3.1. Чтение (живая форма → XML) — ред. 2 (К1, М2 ревью Kimi)

```
если контейнер isModified=true → ОТКАЗ «есть несохранённые правки — чтение отражает
только сохранённое состояние» (без побочных действий; config_save в чтении ЗАПРЕЩЁН —
он бы тихо закрепил чужие несохранённые правки человека, К1)
cf последнего сохранённого состояния (cfg_archive_cf, кэш cf по времени)
temp_read (раз на cf, mockup_init --from): /DumpConfigToFiles -listFile
(Документ.X.Form.Y) → XML формы
```

* Кэш **безусловный** `form_hash → XML` (М2): XML управляемой формы самодостаточен,
  внешние зависимости — ссылки по uuid, стабильные. Чужие сохранения не инвалидируют
  кэш; пересборка temp_read — только для формы, которой нет в кэше, на свежем cf.
* Свежесть формы против cf (К1): хеш живого текста (`form_save`) против текста из cf
  (`cf_extract_text`) с **шапка-нормализатором из П1** — расхождение = несохранённая
  правка этой формы → отказ (XML отражает cf).
* Ловушка: cf = последнее СОХРАНЁННОЕ состояние («Нет» на вопрос об изменениях).

### 3.2. Запись (XML → живая база) — ред. 3 (по вердикту П3 28.10.2026)

Запись через живой редактор НЕ РАБОТАЕТ (П3 §4.3): form_load меняет только буфер
редактора, ни один механизм коммита правку в конфигурацию не забирает. Рабочая цепочка —
через cf2 и /LoadCfg при закрытом конфигураторе:

```
предусловие: контейнер isModified=false; снимок состава владельца формы
(реквизиты/ТЧ/имена) в живой базе == снимку на момент чтения XML (К2: Identifier
не ловит удалённый реквизит); form-validate XML (скилом, вне сервера)
cf живой базы (cfg_archive_cf, кэш по времени) → temp_write (ОТДЕЛЬНАЯ база записи,
  пересобирается из свежего cf на КАЖДУЮ запись — М3)
/DumpConfigToFiles формы из temp_write → исходный XML (канон платформы)
правка XML (вызывающий; form-validate скилом) → /LoadConfigFromFiles
  (listFile = ПУТИ файлов, UTF-8)
ПОСТУЛОВИЕ (М5): re-dump этой формы из temp_write ПОБАЙТНО равен выгрузке после
  первой загрузки (канон платформы) и содержит признак правки — иначе отказ ДО /DumpCfg
/DumpCfg temp_write → cf2
конфигуратор живой базы закрывается → /LoadCfg cf2 → /UpdateDBCfg → открывается
ВЕРИФИКАЦИЯ:
  (а) текст формы из свежего cf живой базы == тексту из cf2 (нормализатор шапки+EOL)
  (б) form_save живой содержит признак правки (детерминирован, §4.1)
расхождение → полный круг §3.1 как диагностика
```

* Распаковка cf (бывшая критическая зависимость) — решена Python-парсером (§4.1);
  блокером стал коммит буфера редактора (П3) — цепочка обходит его через /LoadCfg.
* Цена пути: на конфигурации 2 ГБ cf_archive_cf ≈ 129 с, temp_write ≈ 6 мин,
  LoadCfg+UpdateDBCfg ≈ 1,5–6 мин (замеры §4.2/П3) — писать форму целиком дороже
  чтения; это цена отказа от реверса движка.
* isModified после /LoadCfg=false (загружено сохранённое состояние); отдельная отметка
  не нужна. Способ round-trip prop_set остаётся в каталоге (маркер для других сценариев).

### 4.1 Итог П1 (27.10.2026) — положительный

**Инструмент:** `server/tools/cf_inspect.py` — чтение контейнера cf/epf без платформы.
Формат: внешний конверт (универсальная заглушка, байт-в-байт одинакова у всех cf) +
вложенное хранилище объектов (блоки `\r\n<size> <page> <next> \r\n`, данные raw-deflate
`zlib wbits=-15`; записи `<uuid>` + `<uuid>.0` (сериализация) + `<uuid>.2` (модуль,
info+text) + `root`/`version`/`versions`/`deleted`). Записи ищутся по **uuid формы** —
uuid разрешается в живом/временном конфигураторе (`md_children` владельца); внутренней
линковки «объект→формы» в cf нет (дерево хранит плоские списки по классам) — для
пайплайна temp-базы это не нужно.

**Карта отличий «cf-текст vs form_save-текст»** (ОбщаяФорма.МсрФормаСервер, empty2,
cf mcp-20261027-231440): 76 строк, **75 байт-в-байт совпадают**, единственное отличие —
строка 7, поле имени активного элемента в шапке редактора
(`{-1,02023637-…},0,0,0,9,"ФормаКоманднаяПанель",` у form_save vs `…"",` у cf).
Разница размеров ровно 40 байт = длина имени. **Нормализатор:** очистить это поле —
после него тексты идентичны.

**Обратная запись проверена живьём:** form_load(cf-текст, expected_hash от form_save)
→ `loaded:true`, затем form_save → **байт-в-байт равно cf-тексту**. Процедура: файл
как есть (UTF-8+BOM, CRLF), без перекодировок. Боевые формы ГисМарка из cf извлекаются
(190 КБ, 6419 строк, inline-XML в `{#base64:…}` декодируется) — сравнение с живым
form_save на mockup-gm переходит в П2.

**Решение по мосту:** мостовыe cf-операции (cf_records/cf_read_record/cf_scan) убраны —
attachStorage не распаковывает deflate; чтение cf — только cf_inspect.py (работает без
конфигуратора).

### 4.3 Итог П3 (28.10.2026, empty2) — чтение и круг через cf2 работают, запись через живой редактор НЕ работает

**Отрицательный результат пробы (главный):** `form_load` меняет **только буфер редактора
формы**. Правка не попадает в конфигурацию ни одним из проверенных способов:
config_save (забирает старое состояние), маркер isModified через prop_set round-trip
(ставит признак, но буфер не сбрасывает), Frame.FileSave(4) «Сохранить документ»,
Frame.FileClose(3). Буфер переживает закрытие документа и потерю фокуса. Спайк
«isModified после form_import не выставляется» получил причину: form_import не
изменяет конфигурацию вообще. raw-сторона свойства (IMDExtObj) сериализацию не
поддерживает, из JS недоступна — запись формы требует патча движка Снегопата (реверс,
вне этапа).

**Рабочий записной круг (подтверждён живьём, П3):**
```
cf живой базы → temp_write (mockup_init --from) → /DumpConfigToFiles формы → XML
→ правка XML → /LoadConfigFromFiles (listFile = ПУТИ файлов, UTF-8;
  «ОбщаяФорма.X» именем объектом НЕ грузится) → ПОСТУСЛОВИЕ М5: re-dump содержит
  признак правки (edit_marker) + повторная загрузка канона даёт байт-в-байт ту же
  выгрузку (платформа переформатирует XML — канон = выгрузка платформы)
→ /DumpCfg → cf2 → конфигуратор живой базы ЗАКРЫТ (предусловие isModified=false)
→ /LoadCfg cf2 → /UpdateDBCfg → конфигуратор открывается →
верификация: form_save живой содержит правку ✓; cf живой базы == cf2 (обе
платформенные сериализации)
```
Замеры empty2: temp_write 3,7 с; LoadConfigFromFiles 1,5 с; re-dump 1,5 с; DumpCfg 1,3 с;
LoadCfg+UpdateDBCfg в живую базу ~3 с.

Уточнения протокола: платформа переформатированный XML выдаёт канонически
(раскрывает `<Title>` в строки, добавляет ExtendedTooltip) — побайтовое равенство
достижимо между ДВУМЯ выгрузками платформы, не между рукописным XML и выгрузкой.
Нормализатор шапки дополнен выравниванием EOL (тексты форм смешивают CRLF и CR).

**isModified-маркер:** round-trip `prop_set` (то же значение) выставляет признак
изменения без дельты содержимого — годится как способ отметки.

**Негатив К2:** механизм снимка подтверждён — `md_children` состава до/после правки
(переименование) детектирует изменение и откат (временный объект создан/удален;
md_add_child на пустых Реквизитах и после перезапуска упирается в навигацию дерева —
известная граница). Встраивание отказа в form_set_xml — в реализации.

### 4.4 Итог П4 (28.10.2026, mockup-gm) — приёмка пройдена, с отклонением по «копии»

Объект приёмки: ОбщаяФорма.МсрПриёмка (своя форма макета, создана конструктором
7C63B0CB, сохранена config_save). Отклонение от плана: «копия боевой формы» заменена
собственной формой — перенос содержимого вендорской формы в свою по XML влечёт
привязки данных (ElementDataPath на реквизиты вендора) и решение о поддержке, это вне
этапа (М6). Полнота состава уже доказана на большом вендорском образце (§4.2: 789/791
имён элементов в XML).

Цепочка form_set_xml на mockup-gm (конфигурация 1,97 ГБ), живьём:
cf 132 с → temp_write 330 с (антивирусная блокировка — ретраи) → dump/load/postcondition
→ cf2 → закрытие конфигуратора → /LoadCfg cf2 → /UpdateDBCfg 19 с → переоткрытие →
**верификация: МсрКнопкаП4 в живой form_save ✓; cf живой базы == cf2 по тексту формы
(нормализатор) ✓; элементов в XML 1 → 1 (ничего не потеряно) ✓; isModified=false ✓**.
Негатив К2 на макете: правка имени владельца между чтением и записью → отказ до записи
(первый рубеж isModified; сравнение снимков — рубеж П3).

Доведено по ходу приёмки: постусловие М5 в tool — признак правки (edit_marker) в
re-dump + идемпотентность двух выгрузок платформы (рукописный XML платформа
переформатирует — байты не равны, П3); _kill_session — сначала taskkill без /F
(жёсткий kill оставляет .cfl и роняет следующий пакетный вызов «1Cv8.cdn. Схема не
зарегистрирована»); ретрай пакетных вызовов;mockup_init ретраит удаление свежезалитой
базы (антивирус). Известная дыра инструмента: перед записью надо гасить ВСЕ конфигураторы
базы (зомби-сессия от прошлого прогона держала 1CD 3 минуты — ретраи не спасли) — в
реализации: kill по всем сессиям с conn этой базы.

**Свежесть вендорских форм (замер П2).**
Для форм, сохранённых платформой вендора, cf-текст ≠ form_save-текст даже без правок:
выровненный diff (29 194/29 202 строк равны) — 4 блока: счётчик 2→4 и две доп. записи
(индексы 25/26) в коллекции шапки, доп. поле `19,{"S",""}` в середине, уплотнение
inline-XML. Это **нормализация сериализации редактором 8.3.27**, а не правка человека.
Следствия: (1) hash-сверка «cf-текст vs form_save» валидна только для форм, записанных
текущей платформой (наши правленые формы и cf2 после form_set_xml); (2) для вендорских
форм её пропускаем — несохранённые правки человека и так отсекаются предусловием
isModified=false (правка в редакторе формы выставляет признак изменения контейнера);
(3) контроль чтения — побайтовое сравнение XML из temp_read, не внутреннего текста.
Повторный form_save той же формы детерминирован (байт-в-байт, hash 228a7f20).

Единица правки для приёмки — свойство существующего элемента (заголовок) и добавление
элемента; «перетащить/удалить половину формы» вне приёмки. **Скоуп (М6): основная
конфигурация; расширения и формы на поддержке — вне этапа 8** (боевые формы ГисМарк
на поддержке — отдельное решение владельцу).

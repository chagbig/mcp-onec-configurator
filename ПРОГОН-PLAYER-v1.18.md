# Живой прогон player (v1.18) — инструкция по сбору отчёта о пробелах покрытия

## 1. Зачем этот прогон

`player` (73-й инструмент) превращает запись ваших действий в конфигураторе в
**отчёт о пробелах покрытия моста**: какие ваши привычные операции агент уже
умеет (covered_op), какие идут через меню (menu_invoke), а каких в MCP-сервере
нет вовсе (uncovered — кандидаты в новые инструменты v1.19). Несколько часов
вашей обычной работы дают точный список того, что автоматизировать дальше.

Безопасность записи: логируются **только VK-коды клавиш** (символы/пароли не
попадают в лог) и координаты/кнопки мыши + заголовок активного окна. JSONL
приватный — в репозиторий не кладите.

## 2. Подготовка (5 минут)

| Шаг | Как проверить |
|---|---|
| Сервер v1.18.0 установлен, конфигуратор открыт | `ping` в ZCode отвечает pong; `list_sessions` показывает pid |
| Журнал моста включён (для coverage) | `journal_configure` без аргументов → `enabled: true`; журнал пишет в `<HomeDir>\mcp\journal\<pid>.jsonl` |
| RDP-сессия подключена | LL-хуки пишут только при активной сессии станции |
| Каталог для логов | предложите `<HomeDir>\mcp\player-logs\` (вне репо) |

## 3. Запись действий (30–120 минут)

В отдельном окне PowerShell:

```
cd <путь к установке>\mcp-configurator\server\tools
python user_watch.py --pid <pid конфигуратора> --secs 3600 --out ..\..\..\mcp\player-logs\session-01.jsonl
```

- `--secs` — длительность в секундах (3600 = час; можно остановить раньше
  Ctrl+C — лог уже записан построчно).
- Во время записи **работайте как обычно** в конфигураторе: метаданные,
  модули, формы, расширения, хранилище, меню — всё, что делаете в реальной
  работе. Чем типичнее работа, тем ценнее отчёт.
- Не обязательно делать всё за один присест: запишите 2–3 сессии
  (`session-01/02/03.jsonl`), прогон обрабатывает их по отдельности.
- Важно: если в какой-то момент вводите пароль/конфиденциальные данные —
  не страшно (символы не логируются), но окно с паролем лучше держать вне
  конфигуратора.

## 4. Разбор лога (5 минут на сессию)

Три команды (CLI) либо MCP-инструмент `player` — одинаковый результат.

### 4.1 Классификация — что вы делали

```
python player.py classify --user ..\..\..\mcp\player-logs\session-01.jsonl --out report-classify.json
```

В ответе: `stats` (сколько covered_op / menu_invoke / uncovered) и каждое
действие с классом и `suggest` — каким инструментом моста оно закрылось бы.

### 4.2 Аудит покрытия — главный артефакт

```
python player.py coverage --user ..\..\..\mcp\player-logs\session-01.jsonl --mdjournal ..\..\journal\<pid>.jsonl --out report-coverage.json
```

- `--mdjournal` — журнал моста той же сессии: каждый uncovered получает
  `md_followed_s` — зазор до ближайшего последовавшего изменения метаданных.
- **Uncovered с малым `md_followed_s` (до ~2 с) = вы кликнули, а конфигурация
  изменилась, но моста-инструмента для этого нет. Это самые ценные строки** —
  прямые кандидаты в v1.19.
- Если журнал пуст: `journal_configure` (enabled=true) и повторить сессию;
  coverage без mdjournal тоже полезен, но без приоритизации.

### 4.3 Сводка по всем сессиям

Повторите coverage для каждой session-NN и сложите сводку: сколько всего
uncovered, какие повторяются (одна и та же операция в нескольких сессиях —
приоритет высший).

## 5. Воспроизведение (опционально, только при свободной станции)

`replay` повторяет записанные действия. Сначала всегда dry-run:

```
python player.py replay --user ..\session-01.jsonl --session-pid <pid> --dry-run --out plan.json
```

План (`plan.json`) — что будет сделано, без единого ввода. Исполнение:

```
python player.py replay --user ..\session-01.jsonl --session-pid <pid> --yes --out replay-run.json
```

Гарантии и правила:
- **станция должна быть свободна** — перед первым вводом гвард проверяет
  foreground (должно быть активно окно конфигуратора); при вашей занятости
  откажется, а не уйдёт в чужие окна;
- клики исполняются **из тика моста** (mouse_click) — 1С станционные клики
  игнорирует; клавиши — со станции (1С их принимает);
- темп записи воспроизводится (паузы между действиями сохраняются);
- в конфигураторе при этом произойдут РЕАЛЬНЫЕ изменения — запускайте на
  тестовой базе (empty_mcp/empty2), не на рабочей.

Если план подозрителен (длинный, есть «окна» с большими паузами) — ограничьте
окно: `--start "2026-11-17T10:00:00Z" --end "...Z"` или `--max 20` (первые 20
шагов).

## 6. Что прислать разработчику (формат обратной связи)

Для каждой сессии: **report-coverage.json + краткий текст**:
- топ-5 uncovered по частоте (клик → что делали в конфигураторе своими словами);
- все uncovered с `md_followed_s` < 2 с — «я сделал то-то, конфигурация
  изменилась, а инструмента нет»;
- если replay исполнялся — replay-run.json и что пошло не так.

Файлы приватные — передавайте локально (шара/почта), не в публичный репозиторий.

## 7. Типовые проблемы

| Симптом | Причина / действие |
|---|---|
| user_watch: 0 событий | RDP-сессия не активна — подключитесь к станции |
| coverage: `md: 0 событий` | журнал моста не включён — `journal_configure` (enabled=true) и повторить сессию |
| coverage: uncovered без md_followed_s | не передан `--mdjournal` или журнал другой сессии |
| replay: «foreground» отказ | окно конфигуратора не на переднем плане — активируйте и повторите |
| replay: клик не попал | окно конфигуратора переехало/поменялся масштаб DPI после записи — перезапишите сессию |
| uv run на Python 3.14+ | ставьте на Python 3.11–3.13 (см. issue #24; v1.18 ограничил win-ui) |
